§1 The one rule

Everything is an event on the bus

No driver ever calls another driver. A Sense publishes; anything that cares subscribes. One task drains the queue, so handlers run in a single context and never need their own locks. This single decision is why a new sensor can be added without touching a line of existing code.

Subscriptions match an exact name (touch.pet), a family (touch.*), or everything (* — how the debug tracer and the Berry host listen). Events published inside a handler land in the next drain, not the current one, which keeps cascades from recursing.

§2 Components

Four primitives, one component each

Every feature must present itself as a Sense (input → events), an Expression (actions → output), a Reflex (event → action logic, in script), or a Skill (an LLM-mediated capability, v2+). The directory layout follows the same split.

Note what main is: not a god object, just wiring plus the single framework-owned reflex that turns a Brain reply into expressions. Everything else is a component that could be deleted without breaking its neighbours.

§3 Concurrency

Nine tasks across two cores

Network and TLS live on core 0 with the bus dispatcher; everything that must stay smooth — rendering, sensing, the LED ring — lives on core 1. The rule of thumb: anything that can block for seconds goes on core 0 and talks to the rest of the system only through the bus.

TaskCoreStackPrioPeriodWhy it exists

The Brain never blocks the bus: brain.ask handlers just strdup the prompt onto a 4-deep queue and return. If the queue is full the ask is dropped rather than stalling the whole creature.

§4 Portability

Hardware is a build-time choice, not a code fork

Each display and mood-indicator backend is a whole source file guarded by its Kconfig symbol. Exactly one compiles in; the rest vanish. Every backend implements the same two entry points (face_start(), led_start()) and consumes the same events — so a pack written for the round colour face works unchanged on the monochrome OLED.

§5 The Brain

        
One contract, three possible brains

        
The firmware never names an AI vendor. It publishes brain.ask and waits for
          brain.reply. Today a device-side adapter fills that contract by calling Claude
          Haiku directly over TLS; tomorrow a hub server can serve the identical contract; with no
          network at all, nothing fills it and the reflexes simply keep running.

        

          
Default · today
On-device adapter

            
WiFi + an API key. One persistent TLS connection, reused across asks.

          
Optional · v2
Hub server

            
Same contract over LAN. Unlocks webhooks, OAuth integrations, long-term memory.

          
Always
No brain

            
Offline, reflexes still fire. The buddy is quieter, never bricked.

        

        
// device → brain
{ "event": "touch.pet", "personality": "…", "sensors": {…} }

// brain → device (parsed defensively: the model loves ```json fences,
// so the framework extracts the outermost {…} rather than trusting framing)
{ "utterance": "All forgiven!", "emotion": "happy" }

        
Two hard-won details live in this path: the reply parser tolerates markdown fences, and the
          TLS connection is kept alive because on the classic ESP32 a fresh handshake costs 3–6 s of
          software elliptic-curve maths — enough to trip the task watchdog.

      

    


    
    

      

        
§6 Behaviour is data

        
Emotions are a table, not a code path

        
An emotion is five integers, a blink temperament and a colour. The renderer and the LED ring
          read the same row, which is why the eyes and the halo can never disagree. Click a row — the
          eyes below are drawn by the same algorithm the firmware runs.

Above the table sits the layer nobody recompiles: Berry
          reflexes. Scripts are uploaded from the device's own web UI, which writes the file
          and publishes system.reload; the host tears the VM down and rebuilds it in place.
          Editing behaviour never involves a flash cable.

        
# packs/zero/reflexes/main.be — hot-reloaded, no rebuild
buddy.on("touch.pet", def (ev)
  buddy.face.emotion("happy")
  buddy.led.mood("excited")
  buddy.say("The user just petted you gently.")   # → brain.ask
end)

        
The VM lives entirely on the bus dispatch task, so scripts need no locking — and equally, a
          script that loops forever freezes every reflex. That constraint is the price of the
          simplicity.

The 240×240 framebuffer (112 KB) lives in PSRAM;
          DMA and WiFi buffers must stay in internal RAM. Two crashes taught these limits the hard way:
          app_main overflowing its default 3584-byte stack while bringing up the LCD and the
          VM together, and a text-wrap buffer overrun that corrupted the heap on long replies. Both are
          now fixed, and both are documented in the hardware notes so nobody re-learns them.

      

    


    
    

      

        
§8 Extending

        
Adding something new

        

          
New behaviour
Write a reflex

            
A few lines of Berry in the web editor. No toolchain, no rebuild, live in seconds.

          
New sensor
Add a Sense

            
One .cpp, a task, and bus().publish(…). Nothing existing changes.

          
New output
Add an Expression

            
Subscribe to an action event and drive the hardware. Same isolation.

        

        
The honest limits of the current design, worth knowing before you
          build on it: the emotion table is still compiled in rather than supplied by a pack; the Brain
          call is non-streaming, so the face can't react mid-sentence; and there is no audio path yet —
          chirps and the push-to-talk voice loop are the next milestone.
